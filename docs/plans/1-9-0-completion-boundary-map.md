# 1.9.0 — the completion-boundary map (#1507)

The design map #1507 asks for: one map, one PR per step, extraction only. It carries the 1.7.5
recovery map's rules (`docs/plans/1-7-5-recovery-extraction-map.md`) to the three methods that
map named out of scope, and it adds one thing that map didn't have to: **a named seam** where the
cycle's terminal outcome is known, which is what 2.0's Campaign lands through (the 1.9.0 plan,
§1–§3.2).

## 1. The invariant

> **Moving the run and cycle spine does not change what a run or a cycle does.**

Proven the way 1.7.5 proved it:
- **The goldens stay canonical-JSON-identical** across every PR (§3.2). A PR that regenerates a
  golden has changed behaviour and is not an extraction PR.
- **The unit suites that pin the moved code pass unedited,** apart from a call site that moves
  with its method, which is named in the PR.
- **The diagnostics reach their seams on the pinned deploy.** 1.9's set (plan §4) reads
  "behaviour held equal", with L1 on every counted roll and functional yield at 1.8.2's level.

## 2. The subject, measured on main `d88f1fe6` (2026-09-29)

Tests call the three methods directly (32 call sites for the plan gate alone). Each moved method

### 3.4 The diagnostics, by block

| diagnostic (plan §4) | reaches |
|---|---|
| every cycle | step 1's gate (the `progress_plan_review` gate after framing); step 3's sequencing and completion |
| `unattended-chain` (cancel, crash, hang) | step 2's terminal mapping and finalisation on three paths; step 3's end on a failed or cancelled run |

## 4. The map: one PR per step, in this order

### Step 1: the framing-gate plan check leaves the executor

A collaborator, `FramingGateCheck` (`adapters/cycles/framing_gate_check.py`), constructed where
`PatchAcceptance` is. It gets the artifact vault and the cycle registry.
- **Moves:** the method's body, and the helpers only it calls: `_validate_interface_manifest`,
  `_validate_contract_binding`, `_store_rejection_record`, and `frozen_check_violations`' call.
- **Stays, and is passed in:** `_is_bind_mode`, `_load_seeded_manifest_content` and
  `_load_contract_for_run` are shared with `execute_run` and the dispatch-time net. They stay on
  the executor, and the collaborator receives them as callables, as `PatchAcceptance` receives
  `reexecute_repaired_suite`.
- **The executor keeps** `_reject_invalid_plan_before_workload_gate` as a one-line delegate.
  #663 D5's ownership note (two nets, different error channels) moves with it verbatim.

### Step 2: `execute_run`, by concern

Three collaborators, and what's left is the run's spine:
- **`RunProvisioning`** (`adapters/cycles/run_provisioning.py`): load and mark running,
  checkpoint restore, the plan/contract/manifest load, `generate_task_plan`, build-only
  validation, and skeleton seeding. It returns a typed provisioned run (plan, contract, manifest,
  checkpoint), so the spine never re-reads what provisioning decided.
- **`RunAdmission`** (`adapters/cycles/run_admission.py`): the reserve-buffer guard and
  recruitment, returning the recruited ids. The `finally`'s release and sweep move with it, as
  one `release(run_id, recruited)` method, so what admits a participant also lets it go.
- **What's left in `execute_run`:** observability, dispatch within the correlation scope, the
  `except` (already delegating to `resolve_terminal_outcome`), and `RunCompletion.finalize`.
- **As built (2026-09-29).**
  - **The partial-state rule:** provisioning is two calls around admission, `prepare` and
    `seed`, because admission runs between planning and seeding. `execute_run`'s `finally` hands
    finalization whatever cycle, plan and contract the run had reached, so each is recorded on a
    mutable `RunInProgress` on the line after the one that establishes it (register §58). A
    failing-plan run still finalizes with its loaded contract.
  - **Borrowing is by an explicit list of names** (`RunProvisioning.BORROWED`,
    `RunAdmission.BORROWED`), so the moved bodies are token-identical.
  - **One test followed its patch:** `test_correction_runner.py` patched `generate_task_plan` on
    the executor module, where it is no longer looked up.

### Step 3: `execute_cycle`, and the named completion boundary

- **`WorkloadGate`** (`adapters/cycles/workload_gate.py`) owns the inter-workload gate: plan
  re-validation through step 1's check, framing re-rolls, the questions path, and
  returned-for-revision. It returns a typed decision for the loop: proceed, re-roll, revise, or
  stop, with the reason.
- **The sequencing loop** stays in `execute_cycle`, which reads the gate's decision and creates
  the next run.
- **The completion boundary is `CycleCompletion`** (`adapters/cycles/cycle_completion.py`), the
  one place a cycle ends.
  - Every `return` inside the loop becomes a `break` to it, carrying why.
  - It produces a **typed, read-only `CycleEnd`**: the cycle's last run and its
    `RunTerminalDecision`, the reason the loop stopped, and a reference to the cycle's
    `CycleAssessment`. It references the assessment and never recomputes it.
  - It is **the one place a continuation request would enter** (the Campaign SIP's Appendix A).
    In 1.9 nothing enters there. The seam exists, its wiring test covers every way a cycle ends,
    and 2.0 builds on it.
- **The wiring test** (CLAUDE.md, *A changed seam needs a wiring test*) enters at
  `execute_cycle` and drives every terminal path to `CycleCompletion`:
  - the last workload completing;
  - a failed run and a cancelled run;
  - a gate rejected;
  - framing re-rolls exhausted;
  - revisions exhausted;
  - a questions stop.

  Each must produce exactly one `CycleEnd`, with the reason named.
- **As built (2026-09-29).**
  - **`CycleStopReason`** has eight members, one per ending: the seven paths above, split so a
    failed run and a cancelled run each name themselves, plus the single-workload fast path, whose
    run's status says how it ended.
  - **`CycleEnd` carries no separate assessment field.** The cycle's `CycleAssessment` is read by
    its `cycle_id` (`cycle_evidence.assess_cycle`) and isn't stored, so the reference is the id the
    view already carries. The last run's `RunTerminalDecision` is read from its stored loop
    summary (`get_run_loop_summary`), never recomputed.
  - **`execute_cycle` keeps the port's `None` return.** Changing `FlowExecutionPort` inside an
    extraction is out. The view is observed at `CycleCompletion.end`, where 2.0's continuation
    enters.
  - **`WorkloadGate` returns the loop's control flow typed** (`PROCEED` / `RE_EXECUTE` / `STOP`
    with its reason), carrying the loop state the gate body may change. The body is verbatim
    apart from its six exits and the formatter's re-wrapping.
  - **Found while extracting, not fixed here (§5):** the loop stops only on a `FAILED` or
    `CANCELLED` run. A run *paused* by admission (a duty-window deferral, SIP-0089) returns
    normally. It is announced `WORKLOAD_COMPLETED` as `completed`, and its gate runs, rejects the
    empty plan and re-rolls framing, cancelling the paused run. The fix changes behaviour, so it
    belongs in its own PR: **#1754, fixed before the deploy** (the plan's §7a item 6). Any run that
    did not complete now stops the sequence, with `run_paused` or `run_not_terminal` beside the
    two reasons above (`STOP_REASON_FOR_UNCOMPLETED_RUN`, `src/squadops/cycles/cycle_end.py`).

## 5. The forbidden change

No behavioural change rides an extraction PR (the 1.7.5 map, §5). A defect found while extracting
is filed and fixed in its own PR, before or after, and the extraction carries the issue number in
its Evidence. `CycleEnd` is additive: a read-only view that nothing consumes in 1.9 beyond its
wiring test. A PR where it changes an outcome has changed behaviour.

## 6. The stop rule

The map is the scope, and 1.9's set is the clock (plan §4, §8).
- **Core** = steps 1–3. Step 3's boundary is the line's claim, so if the core isn't complete, 1.9
  doesn't cut. The plan says so in the open rather than re-placing the boundary.
- Between steps, only behaviour-neutral debts that touch no step's file land (plan §6 step 5).
  #1701 and #1722 touched the executor, and landed before step 1.

## 7. The harvest

Before each step's PR, the rationale its blocks carry in comments is harvested into
`docs/architecture/defended-bespoke-decisions.md` as numbered entries, keyed to the decision
rather than the move (the 1.7.5 map, §7). Step 1's include: #464/#473 (errors return, and the
caller records a system rejection), #663 D5 (two nets), #424 (a collapsed plan is rejected, an
unreadable one defers), #509 (auto-binding before validation), and pf-42 (frozen-file checks at
the gate).

## 8. Naming

Flat files in `adapters/cycles/`, matching the directory. Each collaborator is named for what it
does, and constructed where `CorrectionRunner` and `PatchAcceptance` are. There's no new package
and no letter or number in a name. `CycleEnd` and `CycleCompletion` are the vocabulary 2.0's
Campaign reads.
