# The inference engine: Ollama or TensorFold (SIP-0111)

The Spark serves the squad's models with one engine at a time: Ollama (in its container, #2249) or
TensorFold (a frozen recipe in `infra/tensorfold/recipes/`). **Only one is ever resident.** Both 27B
checkpoints need most of the box's unified memory, so two engines together can freeze the host.

## Which engine the deploy runs

The deploy's `.env` records it. `COMPOSE_FILE` names `docker-compose.tensorfold.yml` when the
deploy runs on TensorFold, and does not when it runs on Ollama. Every `docker compose` on the box
reads that, so every rebuild and restart puts the model clients on the recorded engine.

```bash
.venv/bin/python scripts/dev/ops/engine_switch.py deploy-engine   # ollama | tensorfold
.venv/bin/python scripts/dev/ops/engine_switch.py status          # what is resident, and the memory
```

Nobody edits `COMPOSE_FILE` for this by hand. The switch writes it.

## Switching

```bash
# To TensorFold: the engine, then every model client, recorded in .env
.venv/bin/python scripts/dev/ops/engine_switch.py to-tensorfold infra/tensorfold/recipes/qwen27b-nvfp4.yaml

# Back to Ollama (the rollback): TensorFold released first, then Ollama, then the clients
.venv/bin/python scripts/dev/ops/engine_switch.py to-ollama
```

**What a switch does:**
- **It holds the box,** and refuses with a run or campaign on it.
- **It stops the old engine, then confirms the release** (no GPU process, 90 GiB `MemAvailable`) before
  starting the new one.
- **On TensorFold, it verifies the server against the recipe** (the served id, the window and the
  command line). It also requires 16 GiB `MemAvailable` after the load.
- **It recreates every running model client** (runtime API and agents) with the provider, URL, key
  and model together, then runs one generation through the deployed adapter from inside an agent.
- **It fails closed.** Any failure restores Ollama, the clients included. Every step is a line in
  `var/engine_switch/<utc>-<command>.jsonl`.
- **It records the deploy it leaves** (`record_deploy.sh`, #2284), TensorFold's container included,
  after a completed switch and after a restoration. A cycle launched afterwards carries a deploy id
  whose record names the engine that serves. A switch that completed but could not record exits 4.

The two directions measured on 2026-10-13: 27 s to TensorFold (kernels cached) and 48 s back.

## Rebuilding

`scripts/dev/ops/rebuild_and_deploy.sh` keeps the recorded engine:
- **On TensorFold,** it does not start Ollama, and the restarted clients come back on TensorFold.
  TensorFold must be serving, or the rebuild refuses and names the switch to run.
- **A TensorFold serving a deploy whose `.env` says Ollama** is a switch left half-done. The rebuild
  refuses it, and never guesses which engine was meant.

## A fresh box

Bootstrap reads the engine from the profile (`config/profiles/bootstrap/<profile>.yaml`):

```yaml
inference_engine:
  engine: tensorfold
  recipe: infra/tensorfold/recipes/qwen27b-nvfp4.yaml   # must be a frozen recipe
```

**On `tensorfold`, bootstrap does three things:**
- It runs `scripts/dev/ops/tensorfold_install.py <recipe>` before the services start: the image,
  built at the recipe's TensorFold commit; the checkpoint and the drafter, fetched at the recipe's
  revisions into `~/tensorfold/hf`; and the kernel caches. Set `HF_TOKEN` for a gated repository.
  The script is idempotent, and `--dry-run` reports what is missing.
- It installs and pulls Ollama as before. Ollama is the rollback.
- At the end, with every service up, it runs the switch to TensorFold.

`squadops doctor <profile> --check squad` checks the profile's squad against the engine's models:
on TensorFold, the recipe's served id, since the adapter serves no other. The Spark's profile
(`local-spark`) serves the squad `full-38-tf` on the frozen NVFP4 recipe (SIP-0111 G4).

The key is the deploy's own: `SQUADOPS_TENSORFOLD_API_KEY` in `.env`, generated by
`deploy_credentials.py` with the server's key file written from it. Rotation is in
`credential_rotation.md`.

## Cycles on TensorFold

An agent takes its squad profile's model before the deploy's. A cycle on TensorFold names a
profile on the served id: `full-38-tf` is the `full-38` roster on `qwen3.8-27b-tf-nvfp4`. The
adapter refuses a model with no frozen recipe.

Every call carries a seed. TensorFold keys an omitted seed to the prompt, so without one a
repeated prompt repeats its answer. A call that sets none gets a fresh seed, and the agent's
`LLM chat_stream_with_usage completed` line names it (`seed=N`). Send that seed with the same
prompt to replay the call (SIP-0111 §9j).

## The memory watchdog, installed once per machine

It runs as a host service, always on, and acts only while TensorFold runs (#2288). Installing it
needs sudo once, as the backup timer does, so it is a deliberate step rather than bootstrap's:

```bash
./scripts/dev/ops/install_host_unit.sh squadops-memory-watchdog            # install and start
./scripts/dev/ops/install_host_unit.sh squadops-memory-watchdog --status   # its state, and its log
```

The service restarts if it stops, and the OOM killer takes it last. One engine switch runs at a time
on the host (`var/engine_switch/.switch.lock`), so its restoration waits for a switch in progress.

## When something is wrong

- **The memory watchdog** (`scripts/dev/ops/memory_watchdog.py`) kills TensorFold's container when
  `MemAvailable` stays under its floor or swap climbs. It then runs `engine_switch.py restore`, so
  Ollama serves and the clients move back. Cycles running at the kill fail, because their engine is
  gone. Its record is `var/engine_switch/<utc>-watchdog.jsonl`, and the restoration's is
  `<utc>-restore.jsonl`.
- **The launch gate** refuses a launch while TensorFold is serving requests the launch did not start,
  or while its authenticated endpoints can't be read (SIP-0111 §5.5).
- **A task whose prompt is larger than the served window** is held (`BLOCKED`), not retried. The
  registry's window and the server's disagree, which is a deploy defect (§5.2).
